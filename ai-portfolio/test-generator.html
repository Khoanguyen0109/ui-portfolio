The Context
Market Research
Testing is entering
a new chapter.
AI is writing it.

QEs have written test cases manually for decades — slow, inconsistent, disconnected from engineering speed. AI changes this by removing the busywork, not the QE — freeing them for coverage strategy, edge cases, and quality gates.

The QE's today
20–40 test cases per sprint, written manually from incomplete requirements. 5–15 min each — mostly reading and parsing, not thinking.
The opportunity
AI handles parsing and drafting. QE spends time on judgment — reviewing, refining coverage, catching what AI misses.
The constraint
QEs must trust the output. Every AI result is reviewable, editable, and never final on its own.

What happens
My design decision
User value + principle
1
QE arrives at the Requirements page
Requirements sync from Jira/ALM automatically. Each shows an AI quality badge — Good, Needs Clarification, or Vague — before opening anything.
Information Architecture
Surface quality signal at the list level, not inside each item
Most tools hide quality issues until the QE opens a requirement. I moved evaluation to sync time — QE scans the list and knows where to focus before spending any time.
User value
No wasted effort on vague requirements — triage happens at a glance
Zeigarnik Effect
2
QE reviews requirement + AI quality breakdown
Full requirement text + AI analysis side by side — what's clear, ambiguous, missing. Score is explained with reasoning, not just shown as a number.
Trust Design
Show the AI's reasoning, not just its verdict
A score alone is opaque and untrustworthy. Showing the breakdown tells QEs exactly what the AI found — builds confidence and teaches better requirement writing over time.
User value
QE trusts the AI output because they can see its work — not just its answer
Aesthetic-Usability Effect
3
QE enriches context before generating
Before hitting Generate, QE can upload attachments — Figma files, DOCX specs, API docs. More context given to AI = more accurate, specific test cases as output.
Input Design · Output Quality
Give QE control over what AI knows before it generates
AI output quality is only as good as its input. I designed this step so QEs can actively improve what the AI sees — attachments feed directly into generation context, making output more targeted and reducing manual edits after.
User value
Better input = better output — QE spends less time editing AI-generated cases after the fact
Goal-Gradient Effect
4
AI asks targeted clarifying questions
For vague requirements, AI generates clarifying questions. QE answers some, all, or none — every answer improves output. Skipping always allowed.
Complexity Management
Offload clarification work to AI, keep QE in choice not obligation
Instead of QE chasing PMs for clarification, AI generates the questions. Live quality score updates after each answer make the value tangible — QE sees progress, not a form to fill.
User value
QE gets smarter output without extra meetings — AI does the legwork
Tesler's Law
5
AI generates test cases
Each test case is generated with: name, precondition, description, and test steps — scoped to the Feature Area. More context + answered questions = more complete coverage.
Mental Model Design
Match the exact structure QEs already write — zero re-learning required
Name, precondition, description, test steps — this is the structure QEs already use in their test management tools. AI output maps directly to what they know, so review starts immediately with no reformatting needed.
User value
Output feels native — QE can review and edit immediately, no mental translation required
Jakob's Law
6
QE reviews, edits, accepts — grouped by Feature Area
Cases auto-grouped by Feature Area. QE edits inline, accepts or rejects in context. No flat list hunting. Accepted cases land directly in the test suite.
End-State Design · Control
Grouping by Feature Area removes the hardest cognitive task — orientation
Flat lists at scale are unusable. Feature Area grouping gives QEs a mental map of what they're reviewing before they read a single case. The final export confirmation closes the loop — it feels like success.
User value
Review is fast and structured — QE stays in judgment mode, not search mode
Peak-End Rule

Lessons Learned
Design Maturity

What I learned,
and what comes next.

01
Core value
AI as a trusted partner — not a threat
AI surfaces quality signals — QE always makes the final call. Every interaction was designed to build trust gradually: score badges, transparent reasoning, always-editable output. 100% voluntary adoption was the proof that QEs felt safe, not threatened.
02
Technical challenge
Multi-agent friction and hallucination
Chaining multiple AI agents introduces real risk: context loss, inconsistent format, hallucination on vague requirements. The clarification step lets QE correct AI assumptions before generation; the review screen catches bad output. We continuously test each agent in isolation and in full flow — this is ongoing, not a one-time fix.
03
Roadmap
Next: AI-powered test execution
Once QE accepts generated cases, the system should run them automatically — capturing results and surfacing failures without manual handoff. From "AI writes tests" to "AI writes and runs tests". Planned as the next phase.
